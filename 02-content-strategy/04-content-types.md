# Handling Different Content Types

Different source material demands different decomposition strategies. Here's how to
approach the most common types.

## Technical Manuals

**Structure pattern:** Setup → Configuration → Usage → API Reference → Troubleshooting

- Each configuration option or API endpoint can be its own page
- Group by functional area, not alphabetically
- Cross-reference heavily — users jump between setup and reference
- Tag by feature name and operation type

## Regulations and Legal Texts

**Structure pattern:** Scope → Definitions → Requirements → Enforcement → Annexes

- Articles or sections become pages (one article = one page, unless very short)
- Group articles by theme, not by article number
- Include the exact regulatory language, then add plain-language explanation
- Tag by article number, obligation type, and affected party
- Cross-reference between requirements and enforcement provisions

## Tutorials and How-To Guides

**Structure pattern:** Prerequisites → Step-by-Step → Worked Examples → Common Pitfalls

- Each major step or phase is a page
- Keep prerequisites in a separate page — don't bury them in step 1
- Worked examples can be their own section if substantial
- Tag by skill level and technology

## Reference Works (Encyclopedias, Dictionaries, Complete Works)

**Structure pattern:** Categorical grouping with consistent page structure

- Each entry or work is a page (or multiple pages if large)
- Consistency matters more than creativity — every page follows the same template
- Heavily tag for lookup — this is the primary access pattern
- Consider a large number of pages; the format handles it (Shakespeare: 725 scenes)

## Certification and Exam Prep

**Structure pattern:** Domain → Concepts → Practice Questions → Key Takeaways

- Align sections with exam domains or competency areas
- One concept per page, with testable detail
- Tag by exam objective and domain
- Cross-reference between related concepts across domains

## The Universal Rule

Regardless of content type: every page should answer a question an agent might ask.
If you can't state the question, the page probably shouldn't exist.
